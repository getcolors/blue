1. Philosophy

  • blue is a small library. A package defines its own steps, wiring and launcher; blue supplies the engine, advice, YAML loading and CLI plumbing. Its only runtime dependency is PyYAML.
  • Steps call tools directly. A step calls gcloud, oci, doctl, hcloud or an HTTP API itself, in Python a coding agent writes and maintains. There is no OpenTofu or Ansible integration: it was removed on 2026-10-29 together with template scaffolding, schema gates, Kubernetes controllers, resource scopes and the subprocess runner.
  • Everything is one dict. Desired state is YAML loaded into opts; every step reads that dict and returns a new one, enriched with what it observed.
  • Idempotent runs. Re-running the same event should converge. create and delete are conventions; the event set is open.
  • Errors are values. Steps report outcome in "blue/exit". Exceptions are caught at the step boundary and converted, so failures route through next_fn and joins like any other result.
  • One model, three languages. Green is canonical; a Red project ports to Blue by mechanical rename.

2. Naming & the opts contract

:green/exit"red/exit""blue/exit"
green.ednred.ymlblue.yml
./green (Babashka)./red (Bun)./blue (uv script)
green.workflowred/workflowblue.workflow
:hello/file"hello/file""hello/file"

Opts is an open dict. blue reserves blue/* and blue.*/*; project state lives under namespace-like keys such as "hello/file".

KeyMeaning
"blue/event"First positional CLI argument: "create", "delete", "rotate", ...
"blue/dry-run"True when --dry-run is passed.
"blue/state-file"Absolute path of the loaded YAML file, so a package resolves its relative paths against the file rather than the working directory.
"blue/exit"Integer outcome. Missing means success and is normalised to 0 after a step.
"blue/err"Error message when "blue/exit" is positive.
"blue/trace"Stack trace when a raised exception is converted.
"blue/step"Current step name, stamped before each step runs.
"blue/branches"Per-branch results at a join or collapsed failed fork.
"blue.workflow/inherited"Private advice-inheritance payload, stripped from public results.
Step input is frozen. The engine deep-freezes opts at each step boundary (FrozenDict, FrozenList; tuple and frozenset members recursively). Unsupported mutable values and custom instances fail before the step runs; callables stay usable. Return new dicts with {**opts, ...}. If a step raises, the failure is built from the frozen input, so partial mutation cannot leak.

3. Steps and errors

A step is a plain sync or async function (opts) -> opts, named by a namespaced string such as "hello/greet". The name anchors wiring, logging, CLI slices, joins and advice.

  • A returned dict without "blue/exit" is success and is stamped 0.
  • Returning a non-dict is a step failure.
  • Raising is allowed: the boundary returns "blue/exit": 1 with "blue/err" and "blue/trace". Raise StepError(message, exit=n) to choose the code.
  • Steps usually branch on "blue/event": any non-"delete" event creates or converges, "delete" removes.
  • Async steps must await everything they start; exec_cli reports a stray unhandled loop exception and exits nonzero.
import asyncio
from blue.workflow import Opts, StepError


async def system(opts: Opts) -> Opts:
    proc = await asyncio.create_subprocess_exec(
        "uname", "-s", stdout=asyncio.subprocess.PIPE, stderr=asyncio.subprocess.PIPE)
    out, err = await proc.communicate()
    if proc.returncode:
        return {**opts, "blue/exit": proc.returncode, "blue/err": err.decode().strip()}
    return {**opts, "hello/system": out.decode().strip()}


def check(opts: Opts) -> Opts:
    if not opts.get("names"):
        raise StepError("names is required", exit=2)
    return opts

failed(opts) is true when (opts.get("blue/exit") or 0) > 0. Without a next_fn, a failed step has no successors and its branch halts.

4. Workflows: wire_fn and next_fn

from blue.workflow import run, step, workflow

wf = workflow(
    start="hello/system",  # required
    wire_fn=wire_fn,       # required static graph
    next_fn=next_fn,       # optional dynamic router
    end=None,              # optional inclusive slice boundary
)
result = await run(wf, {"blue/event": "create", "names": ["alice"]})

wire_fn — the static graph

wire_fn(step, run_opts) returns the step function followed by its default successors, or None for an unknown step. run_opts is the initial opts of the run, so the graph can depend on stable inputs such as "blue/event" but never on values produced during the run.

def wire_fn(step: str, run_opts: Opts):
    return {
        "hello/system": (system_step, "hello/greet"),
        "hello/greet": (greet_step, "hello/report"),
        "hello/report": (report_step,),
    }.get(step)

Several successors form a static fork. The same graph drives join scheduling, so keep the happy path visible in it.

next_fn — the dynamic router

next_fn(step, default_next, opts)  # -> iterable of (next_step, opts) pairs
  • Return nothing to end the branch, one pair to continue, many to fan out in parallel.
  • It sees the step result, including "blue/exit", so it can route failures to cleanup or retries.
  • Without next_fn, a positive exit stops the path; otherwise the default successors run.
def next_fn(step, default_next, opts):
    if (opts.get("blue/exit") or 0) > 0:
        return []
    if step == "hello/system":
        return [("hello/greet", {**opts, "hello/name": n}) for n in opts["names"]]
    return [(s, opts) for s in (default_next or [])]

Composition — a workflow is a step

step(sub_workflow)
step(sub_workflow,
     in_fn=lambda opts: sub_opts,
     out_fn=lambda opts, sub_result: parent_result)

The sub-workflow's result is an ordinary step result, so its exit propagates through the parent's routing. Ambient keys such as "blue/event" and "blue/dry-run" flow in with the default in_fn; advice inheritance survives an in_fn that rebuilds opts from scratch.

Slices

end is inclusive: it runs, then the workflow stops. The CLI's --start and --end override the boundaries for one run.

5. Parallelism, fan-out & joins

  • Static fork: wire_fn lists several successors.
  • Dynamic fan-out: next_fn returns several pairs. Independent successors run as concurrent asyncio tasks.
  • Join: branches from different origins converging on one step run it once, with the deepest shared fork's opts plus "blue/branches".
  • Same-origin fan-out: entries from one fan-out parent at the same step run independently; that is how N-way item processing works.
  • Failure: a failed branch lets siblings finish their current step, collapses the fork, skips the join and propagates the worst exit with every branch result under "blue/branches". On equal codes the first incoming branch's diagnostics win.
Join detection. Convergence is by flat step name. The scheduler waits while another live branch can still reach the step through this run's static graph; dynamic detours invisible to wire_fn need explicit routing care. For a multi-step pipeline per fanned-out item, wrap it in step(sub_workflow) so the items do not join early.

6. Advice

Advice wraps step functions without changing the graph. Registries are immutable workflow values: adding or removing advice returns a new workflow.

from blue.workflow import advice_add, advice_add_all, advice_remove, advice_remove_all, advice_plan

wf2 = advice_add(wf, "hello/greet", "before-while", "hello/policy", allowed)
wf3 = advice_add_all(wf2, "around", "hello/timing", timing, {"depth": -50})
advice_plan(wf3, "hello/greet")   # the composed stack, outermost first
HowEffect
aroundadvice(base, opts); may call the base zero, one or many times.
overrideadvice(opts); the base never runs.
before / afterSide effect before or after the base; the base's result flows out.
before-whileContinue inward only while advice returns truthy (gates).
before-untilUse the advice result when truthy, otherwise the base (fast paths).
after-whileRun advice only when the inward result succeeded.
after-untilKeep a successful inward result, otherwise use the advice fallback.
filter-args / filter-returnTransform opts before the base, or its result after.

Advice may be sync or async. While/until use Clojure truthiness (only None and False are falsy); a step-result dict counts as true when its exit is missing or zero. At equal depth the newest advice is outermost; depth (-100..100, default 0) overrides add order, lower being farther out. Re-adding an id replaces the entry. Through step embeds, the parent's advice is inherited by flat step name, outermost, and a same-id ancestor entry replaces the child's.

7. YAML desired state & COLORS_PAR_*

load_yaml(text) parses desired state with YAML 1.2 core-schema scalars, matching green and red: only true/false variants are booleans (no, on stay strings); 012 is decimal, 0o12 octal, 0x1f hex; scientific notation is numeric; dates and sexagesimal values such as 1:30 stay strings. Empty input loads as {}.

workdir: work
names:
  - alice
  - bob
# Quote version-like values; YAML reads 3.10 as a number.
python-version: "3.10"

Credentials and one-run overrides come from the environment, never from the YAML file. read_pars(opts, env=None) overlays every COLORS_PAR_<KEY> variable onto the flat key <key> (lower-cased, _ to -), coercing to the existing value's type when it was a bool or int. par_name(key) is the inverse. The prefix is shared by all three colors.

from blue.cli import load_yaml, par_name, read_pars

par_name("api-token")                       # "COLORS_PAR_API_TOKEN"
read_pars({"port": 80}, {"COLORS_PAR_PORT": "8080"})  # {"port": 8080}
Keep desired-state keys flat and kebab-case so the overlay can reach them; use namespaced keys for state that steps add.

8. Dry-run, progress & lifecycle

All three are optional and built on advice, not special cases in the engine. Their log lines go through blue.runtime.runtime.log, a mutable seam tests can replace.

  • dry_run.advise(wf, steps) adds around advice "blue.dry-run/skip" to the listed steps. With "blue/dry-run" set it logs dry-run: would run <step> (<event>) and returns success without calling the step. Unlisted steps still run, so read-only discovery can stay live.
  • progress.advise(wf) adds all-step around advice "blue.progress/progress", logging >>> <step> (<event>) and <<< <step> (<n>ms).
  • lifecycle.preflight(original, *, defaults, overlay, validators, after_validate, env) merges defaults, applies an overlay, runs every validator (opts, env, context) and returns exit 2 with all errors joined, or calls after_validate (sync or async). context carries event and real (not a dry run).
from blue import dry_run, progress
wf = progress.advise(dry_run.advise(wf, ["hello/greet", "hello/report"]))

9. The CLI and ./blue launcher

./blue <event> [-f|--file blue.yml] [--start step] [--end step] [--dry-run]
./blue create --dry-run
./blue delete -f prod.yml
./blue create --start hello/greet --end hello/greet
  • run_cli(wf, args, *, default_file="blue.yml", search_parents=False, allowed_events=None) parses arguments, loads the file, applies read_pars, stamps "blue/state-file", "blue/event" and "blue/dry-run", and returns the final opts.
  • An explicit -f always wins; with search_parents, find_up looks for the default file in parent directories only when -f is omitted.
  • A missing or disallowed event, unknown option, missing file or YAML error returns exit 2 before any step runs.
  • exec_cli(wf, args=None, **config) runs run_cli, prints "blue/err" and "blue/trace" to stderr, and exits with "blue/exit".

A package's ./blue is a self-contained uv script: a #!/usr/bin/env -S uv run --script shebang and PEP 723 metadata, holding the workflow, advice wiring and the exec_cli call.

#!/usr/bin/env -S uv run --script
# /// script
# requires-python = ">=3.11"
# dependencies = ["blue @ git+https://github.com/getcolors/blue.git@<commit>"]
# ///
from blue import Opts, exec_cli, workflow

def start(opts: Opts) -> Opts:
    return {**opts, "app/seen": True}

wf = workflow(start="app/start", wire_fn=lambda s, _: {"app/start": (start,)}.get(s))

if __name__ == "__main__":
    exec_cli(wf, allowed_events=["create", "delete"])
Pin by commit. blue is not published to PyPI. Consumers pin a git commit and move the pin with their own procedure (for example uv lock); the in-repo example uses a relative [tool.uv.sources] path.

10. The example

examples/hello is the smallest complete package. Its steps call local CLIs the way a real package calls a cloud CLI:

  • hello/system runs uname -s and stores "hello/system"; a failing command becomes "blue/exit"/"blue/err" and stops the run.
  • next_fn fans out one hello/greet per entry in names; each writes or removes <workdir>/<name>.txt.
  • The branches join at hello/report, which reads "blue/branches" and runs cat over the files on create, or removes the empty directory on delete.
  • A relative workdir resolves against "blue/state-file"; COLORS_PAR_WORKDIR overrides it for one run.
cd examples/hello
./blue create --dry-run   # uname runs; greet and report are skipped and logged
./blue create             # hello alice from Linux ...
./blue delete

11. Testing

uv run pytest runs the suite under tests/ with pytest-asyncio in auto mode; CI runs it on Python 3.11, 3.12 and 3.13.

  • test_workflow.py and test_advice.py pin the engine: routing, freezing, joins, failed forks, composition, combinators, depth and inheritance.
  • test_cli.py pins argument parsing, the YAML 1.2 scalar table and the COLORS_PAR_* overlay.
  • test_dry_run.py, test_progress.py and test_package_conventions.py cover the optional modules and the public export list.
  • test_example_hello.py runs examples/hello in-process and as a script: create, dry-run, delete, the overlay, a failing CLI and the exit codes.

Test a package's own steps by calling them with plain dicts, or stub the CLI they call by putting a fake executable first on PATH.
